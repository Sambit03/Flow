# Database Schema

Complete database schema for the Flow workflow automation platform using Drizzle ORM + PostgreSQL (Neon).

## Overview

The schema is organized into separate files for maintainability:

```
db/
├── index.ts           ← DB connection instance
├── schema/
│   ├── index.ts       ← Re-exports all schema exports
│   ├── users.ts       ← profiles table
│   ├── workflows.ts   ← workflows table
│   ├── nodes.ts       ← nodes table with config types
│   ├── edges.ts       ← edges table
│   ├── executions.ts  ← executions table
│   ├── stepLogs.ts    ← step_logs table
│   └── relations.ts   ← Drizzle relations
├── migrations/        ← Auto-generated by drizzle-kit
├── queries/           ← Query helpers (optional)
├── rls-policies.sql   ← Row Level Security policies
└── README.md
```

## Tables

### profiles

User profile data linked 1-to-1 with Supabase Auth.

**Fields:**

- `id` (uuid, PK) - Mirrors `auth.users.id`
- `email` (text, NOT NULL)
- `username` (text, NOT NULL, UNIQUE)
- `avatarUrl` (text)
- `createdAt` (timestamp with timezone)
- `updatedAt` (timestamp with timezone)

### workflows

Workflow metadata and configuration.

**Fields:**

- `id` (uuid, PK)
- `userId` (uuid, FK → profiles.id, ON DELETE CASCADE)
- `name` (text)
- `description` (text)
- `isActive` (boolean, default: false)
- `webhookSecret` (text) - Generated on creation, format: `whsec_<uuid>`
- `cronExpression` (text) - Optional cron schedule
- `deletedAt` (timestamp, nullable) - Soft delete flag
- `createdAt` (timestamp)
- `updatedAt` (timestamp)

### nodes

Workflow canvas nodes (trigger, action, condition, delay).

**Fields:**

- `id` (uuid, PK)
- `workflowId` (uuid, FK → workflows.id, ON DELETE CASCADE)
- `type` (text) - `'trigger' | 'action' | 'condition' | 'delay'`
- `label` (text)
- `config` (jsonb) - Varies by node type (see schema file for interfaces)
- `positionX` (real) - Canvas X coordinate
- `positionY` (real) - Canvas Y coordinate
- `orderIndex` (integer) - Execution order (0-based)
- `deletedAt` (timestamp, nullable) - Soft delete
- `createdAt` (timestamp)

### edges

Connections between nodes.

**Fields:**

- `id` (uuid, PK)
- `workflowId` (uuid, FK → workflows.id, ON DELETE CASCADE)
- `sourceId` (uuid, FK → nodes.id, ON DELETE CASCADE)
- `targetId` (uuid, FK → nodes.id, ON DELETE CASCADE)
- `branch` (text, nullable) - `null | 'true' | 'false'` for condition branching

**Unique Constraint:** `(sourceId, targetId, branch)` - Prevents duplicate edges

### executions

Workflow run records.

**Fields:**

- `id` (uuid, PK)
- `workflowId` (uuid, FK → workflows.id, ON DELETE CASCADE)
- `status` (text) - `'pending' | 'running' | 'success' | 'failed' | 'timed_out' | 'cancelled'`
- `trigger` (text) - `'webhook' | 'cron' | 'manual'`
- `triggerPayload` (jsonb) - Request body or empty object
- `totalSteps` (integer) - Total nodes in execution
- `completedSteps` (integer) - Nodes completed
- `error` (text, nullable) - Execution-level error
- `startedAt` (timestamp)
- `finishedAt` (timestamp, nullable)

### step_logs

Per-step execution details.

**Fields:**

- `id` (uuid, PK)
- `executionId` (uuid, FK → executions.id, ON DELETE CASCADE)
- `nodeId` (uuid, NOT NULL) - **Intentionally no FK** to preserve logs after node deletion
- `nodeType` (text) - Snapshot of node type
- `nodeLabel` (text) - Snapshot of node label
- `status` (text) - `'pending' | 'running' | 'success' | 'failed' | 'skipped'`
- `attemptNumber` (integer, default: 1) - Retry count
- `input` (jsonb) - Data passed to step
- `output` (jsonb) - Data produced by step
- `error` (text, nullable)
- `startedAt` (timestamp)
- `finishedAt` (timestamp)

**Unique Constraint:** `(executionId, nodeId, attemptNumber)` - Prevents duplicate attempts

## Setup Commands

```bash
cd apps/api

# Install dependencies
npm install drizzle-orm @neondatabase/serverless drizzle-kit

# Generate migrations from schema changes
npm run db:generate

# Apply migrations to database
npm run db:migrate

# Open Drizzle Studio (visual DB explorer)
npm run db:studio
```

## Running Migrations

After editing any schema file:

1. **Generate** the migration SQL:

   ```bash
   npm run db:generate
   ```

   This creates a new file in `src/db/migrations/` with the SQL changes.

2. **Review** the generated SQL in `src/db/migrations/XXXX_*.sql`

3. **Apply** to your Neon database:

   ```bash
   npm run db:migrate
   ```

4. **Add custom indexes** (optional but recommended for performance):
   ```bash
   # Run the SQL from rls-policies.sql in Supabase editor
   # Then add indexes for query performance
   ```

## Row Level Security (RLS)

RLS policies are defined in `rls-policies.sql`. Run these in the Supabase SQL editor **after** applying migrations:

- Each user can only see their own profile
- Each user can only see/edit their own workflows
- Nodes and edges are visible through workflow ownership
- Executions and step logs are visible through workflow ownership

**Note:** The Node.js API uses the Supabase service role key, which bypasses RLS. RLS is a safety net for direct database access — the API enforces ownership manually.

## Soft Deletes

Workflows and nodes use soft deletes (`deletedAt` timestamp):

- Set `deletedAt = NOW()` instead of hard deleting
- Filter queries with `WHERE deletedAt IS NULL`
- Preserves execution history for audit purposes
- Schedule hard delete after 30 days via cron job

## Schema Design Decisions

| Decision                                    | Reason                                       |
| ------------------------------------------- | -------------------------------------------- |
| `step_logs.nodeId` has no FK                | Preserve logs even after node deletion       |
| Node type/label snapshots in `step_logs`    | Logs remain meaningful if node is renamed    |
| Soft delete on workflows/nodes              | Preserve run history and audit trail         |
| `webhook_secret` on workflow                | Validate webhooks without separate table     |
| `cron_expression` on workflow               | Scheduler reads one table instead of joining |
| `attempt_number` on step logs               | Track retries without overwriting data       |
| `totalSteps`/`completedSteps` on executions | Calculate progress without COUNT query       |
| JSONB for config/input/output               | Schema flexibility for different node types  |
